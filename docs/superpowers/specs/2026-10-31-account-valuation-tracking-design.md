日期：2026-10-31（香港时间）

状态：设计评审稿；产品方向已讨论，完整设计待用户确认。本文不构成数据库迁移、线上认证配置或部署授权。

代码基线：`db-foundation`，`a6843f42841acf31f343335fab6fa81cc70ca0b9`。实施计划编写前重新核对基线及并行改动。

## 1. 用户目标与首期边界

帮助用户持续回答：**我关注的公司现在的内在价值、安全边际和击球区位置如何，相比关注时发生了什么变化？**

用户已明确的要求：

- 估值是中心，其他公司信息围绕估值解释；遵守价值投资原则，不产生投机、动量或买卖推荐。
- 扣住内在价值、安全边际、击球区，贯穿网站全部研究页面。
- 首期准确、简洁，沿用网站统一估值，暂不开放用户调整估值假设。
- 注册/登录首期同时支持邮箱验证码与 Google；为后续其他社交登录保留接入方式。
- 优先复用免费 SaaS；免费额度和当前配置均须核实。

首期交付：统一账户、全站证券关注、个人估值列表、关注时与最新估值对照、可核对的变化说明、基本账户管理。浏览公开研究页面继续开放。

首期不扩展：个人估值参数、多个自定义列表、投资人关注、长篇笔记与完整判断档案、连续历史图表、邮件估值提醒、组合收益与交易记录、支付与会员权益。后续是否需要这些功能独立验证；本文不设面向用户的免费/收费额度。

准确的含义是来源可追溯、计算口径一致、日期和不确定性清楚。内在价值是模型在特定假设下的估计，不承诺未来价格或损失保护。

## 3. SaaS 与认证选型

采用 Supabase Auth 和现有 Supabase 数据库；登录邮件通过 Resend SMTP。自有登录界面调用官方 SDK，不使用已归档的 `@supabase/auth-ui-react` 或已弃用 auth-helpers。

2026-10-31 官方页面：Supabase Free 包含 50,000 MAU、500 MB 数据库、Social OAuth 与自定义 SMTP；免费项目有闲置暂停及无自动备份等限制。Resend Free 的交易邮件额度为每天 100 封、每月 3,000 封，按邮件数计算，并与同账号其他交易邮件/收件共享相应额度。两项在额度内可以无新增订阅费，当前账单尚未核实。

Google 属于 Social OAuth。本文不包含企业 SAML SSO。不同提供方的配额或附加费用在扩展时单独核实。

`@supabase/ssr` 是官方推荐的 cookie 会话适配包，官方当前仍标 beta。实现时核对并锁定适配版本，保留可重复的会话测试；不通过长期固定过时版本回避升级。

Google 接入前置条件：专用 OAuth 应用、基本 scopes（openid/email/profile）、合适的受众/生产发布状态、有效 Client ID/Secret、Google 端允许的 Supabase callback、Supabase 端允许的本站返回地址。仅配置身份所需权限。

邮箱接入前置条件：有效公开 key、Resend 已验证发信域名、自定义 SMTP、验证码模板/时效/频率限制、生产送达测试。Supabase 默认 SMTP 当前只面向团队地址且为 2 封/小时的测试服务，不能承担正式公开登录。

## 4. 账户体验与页面职责

### 4.1 统一登录

页面显示“使用 Google 继续”和“使用邮箱验证码继续”。首次验证成功完成注册；已有用户直接进入同一账户。首期不增加密码流程。

用户点击“关注估值”时才自然要求登录。保存短期的待完成动作和站内返回位置；取消、失败或超时不显示保存成功。登录成功后由服务端校验证券和最新可用版本，再完成一次幂等关注，回到原页面/语言。若保存的版本比原页面新，反馈明确估值日期，并更新该证券的个人显示；不静默把旧页面数字当成保存结果。

主动从账户入口登录且没有待完成动作时，默认进入“我的估值追踪”。用户从研究深页登录时原路返回。

只接受同源、已知站内路径作为返回目标；拒绝协议相对 URL、外部 host、危险编码与无限回调。待完成动作不含 token、邮箱或客户端提供的估值数字；明确过期且成功后清除。

### 4.2 身份关联与注销

数据归属使用 Supabase user UUID，不以邮箱、Google ID 或昵称为业务主键。相同已验证邮箱的身份使用官方自动关联规则，并在两个登录顺序中验收。不同邮箱保持不同账户；首期不提供自行合并或 beta 手动关联界面。

账户页提供当前邮箱/已关联登录方式、退出登录、删除账户。删除要求近期身份确认并明确说明个人关注与基准引用会删除；服务端验证当前用户后调用管理接口，级联删除个人数据，撤销会话并清除前端状态。其他用户仍引用的共享基准保留。

退出和账号切换时清除个人查询缓存、关注状态和待完成动作。newsletter 是独立偏好：注册、Google 授权、删除个人关注均不能自动改变营销订阅；历史订阅是否继续遵循原订阅状态，账户页明确提供现有退订入口。

### 4.3 全站接入

| 页面 | 首期接入 |
| --- | --- |
| 全站导航（桌面/移动） | 登录状态、我的估值追踪、账户入口 |
| 首页、个股列表、估值筛选 | 可识别证券的轻量关注按钮、已关注状态；沿用现有筛选与估值排序 |
| 投资人详情、买卖榜、共识 | 证券行共享关注动作；机构活动继续作为研究线索，不改写估值或生成买点 |
| 个股详情 | 关注动作；登录且已关注时显示“关注时 / 最新”对照，完整方法与来源仍在原估值区域 |
| 报告和文章 | 已有证券链接/结构化证券引用可进入详情并关注；不重写静态正文，不批量自动解析 ticker 加按钮 |
| 我的估值追踪 | 个人公司列表、当前估值、与基准对照、简短变化说明 |
| 关于、条款等信息页 | 使用全站账户入口；无证券上下文时不放关注动作 |

同一证券在各入口具有同一关注状态，增加/移除后当前浏览器内同步；其他设备重新读取可见。首期不引入 Realtime 服务，跨设备实时推送不是承诺。

### 4.4 个人页信息层级

默认每家公司一行/移动端一块，主要信息是公司、内在价值、估值采用的价格、安全边际、击球区状态。显示估值/价格日期；价格不称实时行情。附一条最需要核对的变化，展开查看关注时与最新数字、计算参照、方法、来源和不可比较原因。

首期使用一个列表，默认按关注时间倒序，保留稳定次级排序；不引入综合机会分、收益榜或多种自定义状态。新增、移除后反馈清楚且可恢复；空列表给出已有个股/击球区入口，不强制填写个人资料或自动关注推荐股票。

币种与每股单位明确；对负安全边际沿用全站现有文案/格式，不把“高于内在价值的幅度”展示成正安全边际。只有零增长底可用时标注实际参照，不能把它冒充可用的中枢 IV。

## 5. 公共页面、用户会话与数据权限

公共研究页面保留现有 SSR/ISR 与 SEO。根布局不读取用户 cookies、不在公共响应刷新会话、不因账户 provider 令整个站点动态化。登录状态与关注状态由小型客户端区域按需加载，列表页批量取状态，不逐行发请求。

建议路由（本稿的实现选择，可由构建者在等价边界内细化）：

- `/login`、`/zh/login`：公开登录界面；OAuth/OTP 使用浏览器公开 key 调官方 Auth SDK，Auth 自身限制频率并支持 CAPTCHA。
- `/my`、`/zh/my`；`/account`、`/zh/account`：私有页面；按请求读取/验证会话。
- `/api/auth/callback`：本站 OAuth 回调，交换 code 建立 cookie 会话。Google Cloud 中的授权回调仍是项目的 `/auth/v1/callback`，两者不同。
- `/api/my/...`：当前用户关注/账户操作；身份由验证后的会话获取。公开 API 或请求参数不得指定其他用户归属。

`/api` 已被语言 rewrite 排除；新增路由必须验证裸英文、中文、语言切换和已有 `/en` 重定向。会话刷新若使用 Next proxy，仅匹配私有页面、认证回调与私有 API，不全站拦截；API 本身仍验证身份，不能只依赖页面/proxy。

用户 Supabase client 每请求新建，使用公开 key 和已验证会话；服务端用 getClaims/getUser 等官方验证方式，不信任 getSession 里的用户对象。私有响应及含 Set-Cookie 的响应使用 `private, no-store`；禁止共享缓存和跨请求用户单例。改变状态的站内接口限制方法、验证 Origin，并拒绝跨站调用。

个人表启用 RLS，读写只允许当前 auth.uid；归属字段、基准内容和估值字段由服务器确定，客户端不能写入任意估值/用户 ID。私有读写采用用户会话，不使用绕过 RLS 的管理客户端。后台基准归档、原子关注操作及删除账户需要的特权必须封装在受控服务端函数中，锁定 search_path、验证调用者、撤销不需要的执行权限；禁止把原有 getDb 暴露给浏览器。

在提供浏览器公开 key 前，核查旧 public schema 表、view、RPC 的 anon/authenticated 权限，收紧后台写入权限；不能只给新增表写 RLS 就认为整个 Data API 已安全。数据恢复、日志和备份不得落入公开 GitHub artifacts。

## 6. 统一估值结果：账户功能的数据前提

新增明确的共享结果契约，继续复用现有 runValuation/deriveValuationVerdict 和全部护栏，不修改现有估值假设、数值门槛或安全边际公式。

记录至少包含：

- 证券身份及来源、币种、每股/ADS 与拆股口径；模型版本、结果契约版本和可追溯版本 ID。
- 实际中枢 IV（可空）、实际比较锚 `reference_value`、`reference_kind`（OE-DCF 中枢 / 零增长底 / SOTP 基础档），显示区间上下沿。
- 估值采用的价格及 price_date；margin_pct、实际所需边际/击球区边界、in_strike_zone、可靠性/可用状态和原因。
- 基本面期末、申报/来源链接（有则记录）、input_hash、利率等外部假设的来源/日期与摘要指纹；计算时刻和发布版本。

数值直接从同一次计算的输入/输出取得。禁止由四舍五入后的安全边际、区间上下沿或显示价格反推出 IV。缺少新契约字段的旧快照必须重新正常计算后才能作为基准，不补猜历史值。

### 6.1 日期与可比较性

关注时间、基准记录时间、计算时间、价格日期、财报期末、披露时间分别保存。关注当天可以记录更早的价格/财报，但界面须如实说明，不能把关注日期标成数据更新日。

比较必须检查证券身份、币种、每股/ADS/拆股口径、reference_kind、模型和契约版本。已验证且可重放的拆股调整可以在显示比较时换算，保留原始基准；无法确认时暂停数值差异和击球区变化判断。模型或参照方法变化时并列展示两份原始结果，标“估值方法已更新，暂不直接比较”，不默默用新方法覆盖历史。

### 6.2 发布与公共缓存

同一版本的内在价值、安全边际、击球区必须在个人页、个股页和列表上相同。个人“最新”只取已成功发布的估值结果，不在每次登录/关注时另跑一套模型。

新结果先准备，按证券完成相关公开缓存刷新并确认代次后才能成为追踪最新版本；发布中/刷新失败继续显示上次已发布版本及日期。可靠性下降、身份隔离或结果被撤销时，独立安全状态在服务端下一次读取时抑制旧的击球区/便宜提示，不等待普通刷新；公开估值区域也必须读取该安全状态。已打开页面在重新进入/恢复可见时刷新相关状态；离线时显示最后确认日期和无法更新的状态，不承诺无 Realtime 情况下瞬时推送。任何旧页面展示保留版本日期，不把跨版本差异写成企业变化。

实施计划必须包含公共数字读取统一、代次确认与失败重试的具体改造，利用现有 valuationPublication 机制；不能只增加个人页读最新表而忽略公共页缓存。源数据请求不因登录而重复，价格更新频率匹配实际入库和发布能力。

## 7. 个人数据与基准生命周期

建议逻辑模型（最终 DDL/索引由实施计划确定）：

| 记录 | 归属与字段 | 生命周期 |
| --- | --- | --- |
| Supabase auth.users | 统一 user UUID、身份及会话 | 由 Auth 管理 |
| user_watchlist | user_id、证券身份 key/冻结身份摘要、ticker 显示值、followed_at、baseline_id、baseline_recorded_at、pending 原因 | 用户拥有；重复关注不重复建行、不重置基准 |
| valuation_baselines | 唯一身份＋发布版本＋内容哈希、完整最小估值契约、来源/日期；不含 user_id 或邮件 | 服务端不可变、去重；多用户引用同一版本 |
| 现有公开最新估值/发布状态 | 最新共享估值和代次，不含个人状态 | 沿用现有发布流水线，按本稿补契约/发布边界 |

不新建完整资料表来复制 Auth 邮箱，也不为每人每天归档估值。只在关注/首次取得基准时归档被需要的已发布结果；未被引用的基准在操作完成后的受控清理中回收。清理必须与新增引用互斥/重试，外键保护有效引用，不采用竞态下先查再删。基准中不记录是谁关注，个人 API 仅返回调用者引用的记录。

证券身份优先复用确认过的 FIGI，或以经过来源核对的发行人 CIK＋证券类别/CUSIP 构成身份键；ticker 仅作显示和导航。身份来源不完整时显示原因，不自动猜同公司/同股份；构建者需在计划中确定与现有证券读取器的映射。首期不自动迁移更名/换码，不把新 ticker 同名或复用视为原证券。身份无法唯一确认时暂不接受关注，公开浏览保留；身份确认但估值不可用的证券可以关注。

关注操作在服务端原子完成：核对身份、读取有效发布代次、去重归档基准、写个人引用。并发重复关注返回现有行；权限失败不留下私人内容；数据库暂时失败保持可重试且不伪报成功。客户端不能上传基准数字。

首次关注时无可用可靠估值：保存关注与明确原因，基准为空。发布流水线在该证券第一次出现可用可靠结果时幂等建立共同基准并补齐仍 pending 的关注；标“首次可用估值”与实际记录时间，不能伪装成关注当日已有估值。观察时点由服务器确定，不由用户是否打开个人页决定。

取消关注会移除个人引用并提供短期撤销；撤销恢复原关注时间/基准，不以最新结果覆盖。若撤销信息已过期或无法恢复，重新关注明确作为新关注。取消关注不影响其他人的基准。删除账户不可作为可撤销关注操作处理。

## 8. 变化说明与异常状态

首期比较对象固定为“关注时基准（或首次可用估值）与最新已发布版本”；不是上次访问，不宣称期间每次进出击球区都已捕获。无新版本/无可见变化时直接显示“与基准相比暂无可确认变化”。

| 证据/状态 | 展示规则 |
| --- | --- |
| 相同模型、身份/每股口径、所有估值输入指纹相同，仅估值所用价格变化 | 可说明“价格变化，估值参照未变”；安全边际显示百分点差异 |
| 基本面 input_hash 或期末更新，来源齐全 | 说明“财务数据已更新，估值结果已调整”；只有完整证据链才解释具体经营驱动 |
| 利率等外部假设更新 | 明确标假设更新，不归因给经营改善/恶化 |
| 同期多类输入变化 | 标“多项估值依据更新”，列可核对项目，不强行给每项贡献百分比 |
| 仅发现结果不同，无法确定完整原因 | “估值结果已更新，具体原因待核实”；不生成 AI 编造的归因 |
| 模型/方法、来源纠错、拆股修复 | 各自标识；无法确认纠错类别时不称公司价值变化；跨口径不计算趋势 |
| 结果失效、过期、缺数据或身份隔离 | 保留关注与原始基准，显示“暂不可评估/待确认”及原因；不等同离开击球区 |
| 可比且可靠的基准/最新 in_strike_zone 不同 | 标“相对基准进入/离开击球区”，只作重新研究提示 |

说明依照上述优先级和异常优先原则确定每行的一条主信息；详细项目展开。差异以原始数值计算，格式化后不可见的小变动不制造摘要；零或异常分母不输出百分比。没有可靠连续历史就不显示连续折线、触发次数或错过机会。

## 9. 成本、恢复与统计

首期复用已有估值发布，不引入按用户重算、付费 AI 解释、额外身份 SaaS、Redis 或 Realtime。基准以版本去重，个人页批量读关注证券；分页、每请求批大小及防滥用限流由构建者定，不把技术防护上限包装成会员额度。

上线前核对数据库实际计费占用、增长速度、Resend 剩余额度和每日发送峰值。超额、暂停或故障时保留数据并提供准确的重试说明；“免费层可启动”不等于有生产 SLA。免费数据库需落实私有异地备份、恢复演练、保留/删除规则；个人邮箱和关注数据不得进入公开 Actions 日志或 artifacts。商业化前重新核对 Vercel 托管适用套餐。

沿用现有分析排除规则与 track 入口，衡量首次成功登录、首次保存、返回追踪、展开对照。事件不得含邮箱、token、关注完整名单或 OAuth 返回参数；成功事件以服务器确认后为准。为跨设备留存关联是否采用最小化的内部标识及隐私告知，由实施计划明确，不在当前研究阶段发送测试事件或改 PostHog 配置。

## 10. 验收与交付顺序

### 10.1 必须通过的用户场景

1. Google 首次注册/再次登录、邮箱验证码首次/再次登录、授权取消、验证码错误/过期/限流，均有准确反馈。
2. 两种登录顺序使用相同已验证邮箱时落同一 user UUID 与关注列表；不同邮箱保持隔离；退出后换账号不残留前一账号数据。
3. 从中英文个股/筛选/投资人证券行发起关注，登录后完成原动作且只保存一次；失败不显示成功；非法返回地址被拒绝。
4. 用户 A 无法通过改 URL、请求参数、RPC、SDK 或缓存读取/修改 B 的数据；未登录者无个人表读写权限，既有后台写表权限得到核对。
5. Google 与邮箱登录的会话刷新、过期恢复、退出、跨设备重新读取可用；个人响应不被 CDN/ISR 公共缓存；公开页面仍有缓存能力。
6. 同一发布版本，首页/列表/个股/个人页的内在价值、安全边际、击球区和日期相同；并发发布与缓存失败不能造成虚假个人变化。
7. 基准固定，重复关注不重置；并发取消/新增/撤销与垃圾回收不破坏引用；无估值关注在第一次可靠发布时生成可追溯基准。
8. OE-DCF 中枢、零增长参照和 SOTP 分支分别验证；不能把 rangeLo 当统一 IV；旧契约缺字段、模型切换、拆股、币种/ADS、身份复用均按规则降级。
9. 演示价格下跌但估值也下修、仅价格变化、基本面与利率共同变化、模型更新、估值失效等样例；不产生伪安全边际、伪经营归因或虚假进出击球区。
10. 手机和桌面均可操作，键盘/焦点/错误状态可用，中英文符合现有文案；空状态、长名称、无数据、慢请求、保存失败与账户删除可恢复/解释。

测试粒度随风险：重点覆盖计算/发布一致性、事务/RLS/账号关联/回调和完整真实登录流程；不为静态文案逐句编写镜像测试。Google 与邮件送达需有实际端到端验收证据，不能由模拟响应或 health 200 替代。

### 10.2 建议实施顺序

1. 统一估值契约、身份核对、发布版本与对照规则；正常重算新契约结果，验证公开数据无数值回归。
2. 个人表/去重基准与 RLS/受控原子操作；在测试环境验证隔离、并发及恢复。
3. 邮箱＋Google、最小账户管理和限定范围的会话刷新；落实公开 key、SMTP、OAuth 及精确回调。
4. 全站轻量入口、个人列表与个股对照；完整用户流程、缓存/成本与上线验收。

阶段顺序可在不削弱数据前提的情况下细分 PR。数据库和线上认证配置需在对应变更可评审后实施，合并与部署按项目授权处理；不得在设计文档 PR 中执行。正式上线前保持账户功能关闭，只有必要数据和认证验收均完成才开放。
